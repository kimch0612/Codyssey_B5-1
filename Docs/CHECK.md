# B5-1 구현 체크리스트 — CLI 기반 Mini Redis

구현 근거는 [Subject.txt](Subject.txt)의 필수 요구사항이다. [Evaluate.txt](Evaluate.txt)의 모든 평가 문항도 점검 범위에 포함하며, 개념 설명은 [Study.md](Study.md)를 참고한다. **보너스 과제는 제외한다.**

각 단계에서 필요한 클래스·함수의 틀을 받은 뒤 세부 내용을 직접 구현한다. 검토 시에는 Git 변경점과 관련 코드를 확인하고, 해당 동작까지 검증한 항목만 체크한다. 설명 점검은 자신의 구현을 근거로 설명한 뒤 체크한다. 문서를 읽거나 틀만 만든 것은 구현 완료로 표시하지 않는다.

단계 번호는 학습을 위한 순서다. 한 단계 안에서도 소단위 하나씩 진행하며, 특정 파일명·클래스 수·보조 함수 구성을 강제하지 않는다. 단, 명세가 요구한 자료구조별 파일 분리는 지킨다. CLI 연결 전에는 내부 객체·함수로 작은 데이터를 확인할 수 있으며, 특정 테스트 도구나 별도 테스트 프로그램 작성은 필수 조건이 아니다.

`SET`·`GET`·`DEL` 등은 여러 단계에서 완성된다. 기본 저장·조회 항목을 체크했더라도 LRU·메모리·TTL·CLI 연결 전에는 해당 명령 전체가 완료된 것이 아니다. 모든 항목은 검증 전 상태로 시작한다.

## 0. 구현 범위와 세부 결정 기록

**근거: Subject 2장·4장·6장·7장**

초기 버킷 수, 특정 해시 공식, 센티널 사용, 지연 삭제, 남은 초 버림, 명령 대소문자 무시는 원문이 지정한 유일한 정답이 아니다. 구현 선택을 원문 필수 조건으로 바꾸지 않는다.

**D1 추가 기록 — 해시맵의 초기 구조:** 초기 버킷 수는 8로 정하고, Python `list`를 버킷 참조를 담는 고정 길이 배열로 사용한다. 각 칸에는 서로 다른 빈 `DoublyLinkedList` 객체를 둔다. 버킷 안의 노드 `data`에는 문자열 `key`와 원래의 `value` 객체를 보관하는 `HashEntry`를 담는 구조를 사용한다. `HashMap`의 내부 상태는 `_capacity`(버킷 수), `_buckets`(버킷 배열), `_size`(저장된 키 수)로 구분한다. 배열 저장소는 칸 확보·인덱스 접근·순회 용도로 사용하며, 키 기반 저장·조회·삭제는 직접 구현한다. 초기 용량, 엔트리 클래스, 연결 리스트 재사용과 속성명은 구현 선택이다. 해시 공식과 없는 키의 반환 규칙은 해당 구현 단위에서 결정한다.

**D1 추가 기록 — 해시 함수의 입출력:** `_hash(key: str) -> int`는 해시 계산과 버킷 인덱스 계산을 함께 담당한다. 반환 범위는 `0 <= index < self._capacity`이며, 같은 키와 같은 버킷 수에서는 같은 결과를 반환한다. 키 수·버킷·엔트리는 변경하지 않는다. 메서드 이름과 두 계산을 한 메서드에 두는 것은 내부 설계 선택이다. 현재 구현은 지역 누적값을 0으로 시작해 문자마다 `(result * 37 + ord(letter)) % self._capacity`로 갱신하고, 모든 문자 처리 후 반환한다. 검증에서 인덱스 범위·반복 호출 결과·저장 상태 유지가 확인됐다. 곱하는 수는 학습자가 42에서 37로 변경했으며, 두 수의 분산상 차이는 Study에 비교 예시로 남긴다. 37 자체가 명세의 필수 상수는 아니다.

**D1 추가 기록 — 버킷 안의 키 탐색:** `_find_node(key: str) -> Optional[Node]`는 `_hash`로 정한 버킷의 연결 리스트를 순회하면서 `node.data.key`를 실제 키와 비교한다. 일치하면 그 리스트에 연결된 기존 `Node` 객체를, 빈 버킷이거나 끝까지 일치하지 않으면 `None`을 반환한다. 키 수·값·노드 연결은 변경하지 않는다. 이 보조 메서드는 필수 연산 `put`·`get`·`contains`·`remove`에 필요한 탐색을 나눠 구현하기 위한 내부 설계 선택이며 별도의 추가 기능이 아니다. 공개 `get`·`remove`의 반환 규칙은 해당 구현 단위에서 정한다.

**D1 추가 기록 — 기본 저장과 갱신:** `put(key: str, value: object) -> None`는 기존 키가 있으면 해당 엔트리의 `value`를 갱신하고 `_size`를 유지한다. 새 키라면 `HashEntry`를 만들어 해당 버킷의 `insert_back`으로 추가하고 `_size`를 1 늘린다. 값 객체는 전달받은 그대로 보관하며, 반환값은 `None`으로 정한다. 뒤쪽 삽입·기존 엔트리 갱신 방식·반환값은 내부 설계 선택이다. 이 단위는 2단계의 기본 저장·갱신이며, 명세가 요구하는 로드 팩터에 따른 버킷 확장은 3단계에서 `put`에 연결한다.

**D1 추가 기록 — 값·존재 여부·개수 조회:** `get(key: str) -> Optional[object]`는 찾은 노드의 엔트리에 보관된 원래 값 객체를 반환하고, 없는 키이면 `None`을 반환한다. 저장된 값 자체가 `None`인 경우와 없는 키는 `get` 결과만으로 구분하지 않으며, `contains(key: str) -> bool`로 키의 존재 여부를 확인한다. `contains`는 값의 참·거짓이 아니라 일치하는 노드의 유무를 기준으로 판단한다. `size() -> int`는 `_size`를 반환한다. 세 조회 메서드는 상태를 변경하지 않는다. 없는 키의 `get` 반환 규칙은 내부 설계 선택이며, CLI 출력 형식은 이후 명령 처리 단계에서 적용한다.

**D1 추가 기록 — 키 삭제:** `remove(key: str) -> bool`는 `_find_node`로 일치하는 노드를 찾고, 해당 버킷의 `remove_node`로 분리한 뒤 `_size`를 1 줄이며 `True`를 반환한다. 없는 키이면 상태를 변경하지 않고 `False`를 반환한다. 값이 `None`이어도 노드가 있으면 삭제 대상이다. 불리언 반환은 삭제 성공 여부를 표현하기 위한 내부 설계 선택이며, CLI의 `(integer) 1`·`(integer) 0` 출력과 구분한다. 현재는 해시맵 안의 삭제를 구현하며, LRU·TTL 등 저장소 전체 구조의 동기화는 해당 후속 단계에서 연결한다.

**D1 추가 기록 — 전체 키 반환:** `keys() -> List[str]`는 모든 버킷과 각 버킷의 노드를 순회해 문자열 키를 한 번씩 담은 새 Python 리스트를 반환한다. 결과 저장소는 `_size`만큼의 칸을 미리 확보하고 인덱스로 채우는 고정 길이 배열 용도로 사용한다. 키가 없으면 빈 리스트를 반환한다. 리스트 반환·미리 확보하는 방식·버킷 번호와 노드 연결을 따라 순회하는 방식은 내부 설계 선택이다. 미리 확보하는 선택은 Subject 7장의 배열 허용 범위를 보수적으로 적용한 것이며, 원문이 특정 초기화 코드나 `append` 메서드 금지를 직접 명시한 것은 아니다. `append`만 사용하는 수집과 현재 수집의 전체 시간 복잡도는 동일하고, 불필요한 `not in` 중복 검색 제거와는 별개의 판단이다. 정렬·삽입 순서 보장은 요구하지 않는다. 값·노드 연결·키 수·버킷 배열은 변경하지 않으며 CLI의 배열 출력은 후속 단계에서 처리한다.

**D1 추가 기록 — 해시맵 확장 보조 메서드:** `_resize(self) -> None`는 현재 버킷 수를 2배로 늘리고, 기존 키를 새 버킷 수로 다시 해싱해 새 버킷 배열에 배치하는 내부 메서드로 정한다. 기존 `HashEntry`와 그 안의 값 객체는 그대로 사용하되 새 버킷의 `insert_back`이 새 `Node`를 만들게 한다. 재배치 자체는 키의 추가가 아니므로 `_size`를 변경하지 않고, `put`도 재사용하지 않는다. 보조 메서드 이름·반환값·엔트리 객체 재사용은 내부 설계 선택이다. 새 키 추가 후 임계값을 판단해 이 메서드를 호출하는 `put` 연결은 다음 구현 단위에서 다룬다.

**D1 추가 기록 — 로드 팩터 계산 보조 메서드:** `_load_factor(self) -> float`는 현재 저장된 서로 다른 키 수 `_size`를 현재 버킷 수 `_capacity`로 나눈 값을 반환하고 상태를 변경하지 않는 내부 메서드로 정한다. 로드 팩터를 별도 메서드로 나누는 이름·반환 형식은 학습 흐름을 위한 내부 설계 선택이며 원문이 요구한 공개 API는 아니다. 0.75 초과 판단과 `_resize` 호출은 다음 구현 단위에서 새 키를 추가하는 `put` 경로에 연결한다.

**D1 추가 기록 — 자동 확장 연결 순서:** `put`에서 새 엔트리를 현재 버킷에 삽입하고 `_size`를 1 늘린 뒤 `_load_factor()`가 `0.75`보다 큰지 검사하며, 초과한 경우 `_resize()`를 호출하는 순서로 정한다. 기존 키 갱신 경로에서는 키 수가 늘지 않으므로 이 검사를 실행하지 않는다. 추가 후 검사하는 순서는 현재 `put` 구조를 유지하기 위한 내부 설계 선택이며, 추가 전에 예상 키 수로 판단하고 먼저 확장하는 다른 설계도 가능하다. 원문 필수 조건은 새 키 추가 결과가 0.75를 초과하면 2배 확장되고, 정확히 0.75일 때는 확장하지 않는 것이다.

**D1 추가 기록 — 최소 힙의 초기 저장 형태:** `MinHeap`은 `(expire_at, key)` 형태의 항목을 Python `list`에 완전 이진 트리 순서로 보관하고, 빈 상태는 빈 리스트로 표현한다. 내부 배열 속성명은 `_items`로 정한다. `expire_at`은 비교 가능한 시각 수치로 `float`, `key`는 `str`로 타입을 표현한다. 우선순위 판단은 첫 번째 값인 만료 시각을 기준으로 하며, 같은 시각 항목의 키 순서는 고정하지 않는다. 별도 개수 속성을 중복 관리하지 않고 `size()`가 내부 리스트 길이를 반환하도록 정한다. Python 리스트는 힙의 배열 저장소로만 사용하며, 내장 힙 API나 전체 정렬로 힙 연산을 대체하지 않는다. 내부 속성명·별도 개수 속성을 두지 않는 방식은 내부 설계 선택이고, 동적 배열 자체 구현은 보너스이므로 제외한다.

**D1 추가 기록 — 최소 힙 삽입과 위쪽 복구:** `push(item: Tuple[float, str]) -> None`는 항목 튜플 하나를 내부 배열 끝에 추가한 뒤, 그 마지막 인덱스를 `_heapify_up(index: int) -> None`에 전달한다. `_heapify_up`은 `(index - 1) // 2`로 부모 인덱스를 구하고 자식 항목의 만료 시각이 부모보다 작을 때 튜플 전체를 교환하며 루트 방향으로 반복한다. 같은 만료 시각은 교환하지 않고 현재 상대 위치를 유지하되, 특정 동률 순서를 외부 규칙으로 보장하지 않는다. `_heapify_up`은 현재 배열의 유효한 인덱스를 받는 내부 메서드로 정한다. 매개변수 형태·동률에서 교환하지 않는 방식·유효 인덱스 전제는 내부 설계 선택이다.

**D1 추가 기록 — 최소 힙 조회와 빈 상태:** `peek() -> Optional[Tuple[float, str]]`는 루트의 기존 튜플을 제거하지 않고 반환하며, 빈 힙이면 `None`을 반환한다. 후속 `pop()`도 빈 힙에서 `None`을 반환하도록 맞춘다. 빈 상태 반환값과 `Optional` 반환 형식은 내부 설계 선택이며 CLI 출력과 구분한다. 힙 항목은 항상 튜플이므로 `None`은 저장된 항목과 혼동되지 않는다.

**D1 추가 기록 — 최소 힙 제거와 아래쪽 복구:** `pop() -> Optional[Tuple[float, str]]`는 빈 힙이면 `None`을 반환하고, 항목이 있으면 기존 루트 튜플을 보관한 뒤 배열의 마지막 항목을 제거한다. 제거 후 항목이 남아 있으면 마지막 항목을 루트에 놓고 `_heapify_down(index: int) -> None`을 인덱스 0에서 호출한 다음 보관한 최소 항목을 반환한다. `_heapify_down`은 왼쪽 자식 `2 * index + 1`과 오른쪽 자식 `2 * index + 2` 중 존재하면서 만료 시각이 더 작은 자식을 선택해 튜플 전체를 교환하고 아래로 반복한다. 두 자식 시각이 같으면 왼쪽을 선택하며, 현재 항목이 선택한 자식보다 늦지 않으면 멈춘다. 마지막 항목을 루트로 옮기는 방식·동률에서 왼쪽을 선택하는 방식·유효 인덱스 전제는 내부 설계 선택이다.

**D1 추가 기록 — LRU 저장 구조 선택:** LRU 리스트의 앞(`head`)을 MRU, 뒤(`tail`)를 LRU로 사용한다. 저장소의 논리 엔트리는 문자열 `key`와 `value`를 가진 별도 `StoreEntry` 객체로 표현하고, LRU 리스트의 노드 `data`에 이 객체를 보관한다. 저장소의 해시맵은 `key`를 LRU `Node`에 연결하여, 키 조회 후 리스트를 다시 순회하지 않고 같은 노드를 `move_to_front` 또는 `remove_node`에 전달할 수 있게 한다. 새 키는 `StoreEntry`를 `insert_front`에 전달하고 그 메서드가 만들어 반환한 LRU 노드를 해시맵에 저장한다. 이미 만든 `Node`를 `insert_front`에 전달하여 `Node.data` 안에 다른 `Node`가 중첩되지 않게 한다. 해시맵 체이닝에 쓰이는 버킷 노드와 사용 순서를 나타내는 LRU 노드는 서로 다른 객체이며, 두 연결 리스트의 `prev`·`next`도 공유하지 않는다. LRU 노드가 키를 포함한 엔트리를 보관하므로 이후 `tail`에서 선택한 제거 후보의 키를 별도 역방향 순회 없이 얻을 수 있다. TTL 표현은 8단계의 D4~D6에서 별도로 결정하며, 이번 선택만으로 `StoreEntry`에 만료 정보를 미리 추가하지 않는다. 이 엔트리 클래스와 `key → LRU Node` 연결은 원문이 고정한 유일한 구현이 아니라 6단계와 이후 자동 제거를 함께 고려해 선택한 내부 설계다.

**완료 확인**

- [x] 순서가 섞인 만료 기록을 넣고 반복해서 꺼내면 만료 시각이 작은 순서로 나온다.

## 5. 기본 문자열 저장소

### 5-2. 삭제·존재·전체 조회

- [x] 덮어쓰기는 최신 값만 남기고 키 수를 증가시키지 않는다.
- [x] 같은 키를 두 번 삭제하면 첫 번째만 성공한다.
- [x] 서로 충돌하는 키나 해시맵 확장에 걸리는 키 수에서도 기본 명령의 결과가 유지된다.

## 6. LRU 추적 연결

**근거: Subject 2장·3장·4장 「LRU」 / 평가 1-2·3-1·3-2**

- [x] 이중 연결 리스트에서 MRU와 LRU가 어느 쪽인지 정하고 일관되게 유지한다.
- [x] 해시맵 조회로 해당 키의 LRU 노드에 직접 접근하게 한다. 키를 찾은 뒤 리스트를 다시 순회해 노드를 찾지 않는다.
- [x] 새 키의 `SET` 성공 시 LRU 추적에 등록한다.
- [x] 기존 키의 `SET` 성공 시 기존 노드를 최근 사용 위치로 옮긴다.
- [x] 유효한 키의 `GET` 성공 시 최근 사용 위치로 옮긴다.
- [x] 없는 키의 `GET`은 LRU를 갱신하지 않는다. 만료된 키의 경우는 9단계에서 확인한다.
- [x] `DEL` 성공 시 데이터와 LRU 추적에서 같은 키를 제거한다.
- [x] 가장 오래 사용되지 않은 키를 리스트의 끝에서 바로 선택할 수 있게 한다.

**완료 확인**

- [x] `SET a A` → `SET b B` → `GET a` 후 MRU는 a, LRU는 b다.
- [x] 기존 키에 `SET`을 반복해도 LRU 노드 수가 키 수보다 늘어나지 않는다.
- [x] 없는 키 조회가 기존 사용 순서를 바꾸지 않고, 삭제한 키가 제거 후보로 다시 나오지 않는다.
- [x] 체이닝에도 연결 리스트를 사용했다면 버킷 연결과 LRU 연결이 서로를 덮어쓰지 않는다.

LRU 갱신 의무는 원문에 명시된 성공한 `SET`·`GET`에 적용한다. 다른 조회 명령의 사용 순서 갱신을 새 구현 요구로 추가하지 않는다.

- [x] OOM 발생 시 D3에 정한 실패 처리와 일치하고, 실제 저장 상태·키 수·메모리 집계가 서로 어긋나지 않는다.

### 7-3. 반복 제거와 메모리 정보

- [x] 저장 가능한 `SET` 후 사용량이 양수 제한을 초과하면 LRU 키부터 제거한다.

## 9. 기본 명령에 TTL 통합·삭제 경로 일치

### 9-1. 키 기반 명령의 선행 만료 확인

- [x] `SET`, `GET`, `DEL`, `EXISTS`, `EXPIRE`, `TTL`에서 해당 키의 만료를 먼저 확인하고, 만료되었으면 삭제한 뒤 없는 키처럼 처리한다.

### 9-2. 덮어쓰기와 모든 삭제 경로

- [x] `DEL`·만료·LRU 제거가 같은 키 수·바이트 집계 규칙을 따르되, `evicted_keys`는 LRU 제거에서만 증가한다.

- [x] TTL이 있는 키를 `DEL`한 뒤 같은 키를 새로 저장해도 과거 기록이 새 데이터를 삭제하지 않는다.
- [x] TTL이 있는 키를 LRU로 제거한 뒤 같은 키를 새로 저장해도 과거 기록이 새 데이터를 삭제하지 않는다.
- [x] 만료된 키를 `GET`한 후 데이터와 LRU에서 사라지고, 사용량은 감소하지만 `evicted_keys`는 그대로다.
- [x] TTL 재설정·덮어쓰기·삭제·재생성이 섞인 순서에서도 현재 유효한 데이터만 조회된다.
- [x] TTL이 있는 기존 키의 OOM 덮어쓰기를 확인하고, 기존 값·TTL·LRU 처리가 D3와 일치한다.

- [ ] `CONFIG SET maxmemory bytes`: 설정 성공 시 `OK`를 출력한다.
- [ ] `INFO memory`: `used_memory:<number>`, `maxmemory:<number>`, `evicted_keys:<number>`를 최소한 포함한다.
- [ ] `EXPIRE key seconds`: 정상 설정 시 `(integer) 1`, 없는 키는 `(integer) 0`을 출력한다. 0 이하 seconds 결과는 D4와 일치한다.
- [ ] `TTL key`: 남은 초, -1, -2를 각각 `(integer) N` 형식으로 출력한다.

### 10-3. 표준 에러와 반복 실행

- [x] 알 수 없는 명령에 `(error) ERR unknown command '<cmd>'` 형식으로 응답한다.
- [ ] 인자 개수 오류에 `(error) ERR wrong number of arguments for '<cmd>' command` 형식으로 응답한다.
- [ ] 정수 파싱 실패에 `(error) ERR value is not an integer or out of range` 형식으로 응답한다.
- [x] OOM에 `(error) OOM command not allowed when used_memory > 'maxmemory'` 형식으로 응답한다.
- [ ] 실행 진입점에서 `mini-redis>` 프롬프트와 입력 → 파싱 → 실행 → 출력 반복을 시작한다.
- [ ] 같은 실행 세션에서 이전 명령으로 저장한 데이터·설정·LRU·TTL 상태가 유지된다.
- [ ] 처리한 명령 오류를 출력한 후 다음 명령을 받을 수 있다.
- [ ] `exit`와 `quit`으로 종료할 수 있다.

## 11. 실제 명령을 통한 통합 확인

**근거: Subject 4장·8장 / 평가 항목 1**

각 흐름은 새 프로그램 실행의 빈 저장소에서 시작한다. 따옴표 사용 여부는 D7에 정한 지원 방식에 맞춘다. 아래 데이터의 값은 모두 공백이 없어 원문이 허용한 두 파싱 방식 중 어느 쪽으로도 확인할 수 있다. 구분용 따옴표는 바이트 수에 포함하지 않는다.

### 11-1. 원문의 메모리 예시

| 순서 | 입력 | 확인할 결과 |
| --- | --- | --- |
| 1 | `CONFIG SET maxmemory 30` | `OK` |
| 2 | `SET user:1 Alice` | `OK`, 엔트리 11바이트 |
| 3 | `SET user:2 Bob` | `OK`, 합계 20바이트 |
| 4 | `SET user:3 Charlie` | 합계 33바이트에서 LRU인 user:1 제거, `OK` |
| 5 | `GET user:1` | `(nil)` |
| 6 | `INFO memory` | `used_memory:22`, `maxmemory:30`, `evicted_keys:1` |
| 7 | `DBSIZE` | `(integer) 2` |
| 8 | `KEYS` | user:2·user:3만 출력, 순서는 자유 |

- [ ] 위 흐름을 실제 REPL에서 실행해 메모리 정보·키 수·키 목록·조회 결과가 모두 일치한다.

### 11-2. GET에 따른 LRU 변경과 여러 키 제거

| 순서 | 입력 | 확인할 결과 |
| --- | --- | --- |
| 1 | `CONFIG SET maxmemory 6` | `OK` |
| 2 | `SET a A`, `SET b B`, `SET c C`를 각각 실행 | 각 2바이트, 합계 6, 제거 없음 |
| 3 | `GET a` | `"A"`, 가장 오래 사용되지 않은 키는 b |
| 4 | `SET d D` | b 제거, 남은 키 a·c·d, 사용량 6, 누적 제거 1 |
| 5 | `GET b` | `(nil)`, LRU 갱신 없음 |
| 6 | `SET e EEEEE` | 단일 엔트리는 정확히 6바이트, 기존 c·a·d를 순서대로 제거 |
| 7 | `INFO memory`, `DBSIZE`, `KEYS`를 각각 실행 | 사용량 6, 제한 6, 누적 제거 4, 키 수 1, 키 목록 e |

- [ ] 위 흐름으로 접근 순서 반영, 제한과 같은 크기 허용, 반복 제거, 누적 카운터를 확인한다.

### 11-3. TTL 초기화와 실제 만료

| 순서 | 입력 또는 동작 | 확인할 결과 |
| --- | --- | --- |
| 1 | `CONFIG SET maxmemory 0`, `SET t old` | 무제한 상태에 t 저장, 사용량 4 |
| 2 | `TTL t` | `(integer) -1` |
| 3 | `EXPIRE t 3`, 만료 전 `TTL t` | 설정 결과 1, 실제 남은 시간과 D4에 맞는 정수 초 |
| 4 | **최초 만료 시각 전** `SET t new`, `TTL t` | `OK`, `(integer) -1` |
| 5 | 최초 만료 시각을 충분히 지난 후 `GET t` | `"new"`, 예전 TTL이 새 값을 삭제하지 않음 |
| 6 | `EXPIRE t 3`, 이번 만료 시각을 충분히 지난 후 `GET t` | 설정 결과 1, 조회 결과 `(nil)` |
| 7 | `TTL t`, `EXISTS t`, `DEL t`, `EXPIRE t 3` | 각각 정수 -2, 0, 0, 0 |
| 8 | `INFO memory`, `DBSIZE`, `KEYS` | 사용량 0, 제한 0, 누적 제거 0, 키 수 0, 빈 목록 |

- [ ] 위 흐름으로 TTL 초기화, 과거 기록 무효화, 만료 선행 처리, 만료와 eviction 카운터의 구분을 확인한다.

### 11-4. 에러 후에도 상태와 명령 흐름 확인

- [ ] 양수 제한보다 큰 단일 키·값에 OOM이 출력되고, 이후 조회·메모리 정보가 실제 남은 상태 및 D3와 일치한다.
- [ ] 정수 파싱 오류, 음수 메모리 제한, 인자 누락·초과, 알 수 없는 명령을 확인한 뒤 정상 명령을 계속 실행할 수 있다.
- [ ] 위 예시 외에도 1~10단계의 완료 확인에서 미검증·실패로 남은 필수 동작이 없다.
